CAN バス経由で URTC ボードファームウェアを更新するための、小さなクロス
プラットフォーム GUI ツールです。`docs/CANBUS.TXT`（本ツールが対応対象と
している同系列の [URTC](https://github.com/JuanenRac/URTC) リポジトリ内に
あります——本ドキュメント末尾近くの「関連プロジェクト」を参照。本 README
内の他のすべての `docs/*.TXT` の参照もそこを指しています）にある、まさに
そのブートローダープロトコルを実装しています：HardwareID チェック、
共有鍵の HMAC-SHA256（非対称署名ではありません）、ゴールデンイメージのバックアップスロット更新フロー、
ブートローダーのハートビートメッセージによるリアルタイムの進捗表示、
そして何を書き込むか決める前に現在何がインストールされているかを確認
できるバージョン照会（このボードのアプリケーション*または*ブートローダー
が CAN 経由で自身を識別するか）。

**更新を確認。** 「更新を確認」ボタンは GitHub に最新リリースを一度だけ問い合わせ、このシステム用でインストール済みより新しいパッケージがある場合にのみダウンロードを提案します。パッケージは、SHA-256 と Ed25519 署名（プログラムに固定されたリリースの鍵）が有効な場合にのみ受け入れられ、確認した後でのみ、転送中ではないときにインストールされます。以前のバージョンは戻れるように残り、新しいバージョンが起動しない場合は自動的に復元されます。自動で確認やインストールが行われることはありません。起動時の確認はオプション（既定でオフ）で、確認の省略は同じウィンドウで警告の後にのみ無効にできます。

ボードと通信する方法は 2 通りあり、どちらも内部では同じプロトコルを
話します：

- **シリアル / SLCAN** —— Windows と Linux の両方で動作します。SLCAN
  ファームウェアを実行する USB-CAN アダプターが必要で、仮想シリアルポート
  として接続されます。
  - アダプターもハードウェアもない場合は、仮想ボードが代わりを務めます。`python -m urtc_can.virtual_board` を実行し、プログラムを起動する前に環境変数 `URTC_VIRTUAL_PORT` にそのアドレス（例：`socket://127.0.0.1:7777`）を指定するか、コマンドラインの `--port` に渡します。ポート一覧に表示され、アプリケーションとブートローダーの両方でボードのように応答します。
- **SocketCAN** —— **Linux のみ**、かつ Linux 上でのみツールの UI に
  表示されます。カーネルの `can0`/`slcan0` ネットワークインターフェース
  と直接通信します。お使いのアダプターがすでに `gs_usb`/candleLight
  ファームウェアで動作している場合（ほとんどの CANable ボードは工場出荷時
  そのままそうです）、このパスは**アダプターの再フラッシュがまったく
  不要**です——Linux 自身のドライバーがネイティブに処理します。

**状態：** 本ツールの CRC32 および HMAC-SHA256 計算は、ブートローダー
自身の C 実装に対してバイト単位で検証済みであり、SocketCAN のフレーム
パッキングは、Linux の `struct can_frame` レイアウトに対してラウンド
トリップのパック/アンパックテストで検証済みです。どちらのプラットフォーム
でも**テストされていない**のは、実際のハードウェア上の実際のボードです——
ブートローダーと通信する新しいツールに対して払うのと同じ注意をもって、
最初の実際のフラッシュ試行に臨んでください：フォールバックとして手元に
JTAG を用意しておいてください。 ここで説明するその他の機能は、シミュレートされたブートローダーである `MockCAN` に対してのみ試されており、実機のボードに対して試したことはありません。

**正直な現状確認 - 実際に今動くもの:** `tests/` には 41 個の pytest ファイル（478 件のテスト：すべて成功、うち 76 件は PySide6 がない場合スキップ）があります——完全なブートローダーシーケンス（開始／消去／受信、ページデータ + PAGE_ACK、HMAC チャンク、本当の成功または特定の `VERIFY_FAIL_REASON` による更新終了）を再現する実際の `MockCAN` トランスポート（`flasher_transports.py`）に対する CAN-OTA プロトコル、署名ルール（公開署名は鍵なしで送信、未署名イメージは拒否、マニフェストの sha256 不一致はバス通信前に拒否）、イメージ整合性チェック、同梱の `firmware/` とそのマニフェストの照合です。GitHub Actions（`.github/workflows/ci.yml`）が push のたびにこのスイートを実行し、`tools/build_test.py` も `build-test.sh`/`.bat` で実行します。ルートにある 2 つの `verify_qt_*.py` スクリプトは pytest の外にある本物のエンドツーエンドチェックです（本物の Qt イベントループが必要。`QT_QPA_PLATFORM=offscreen python verify_qt_*.py` で実行）。`verify_qt_swd_full_chip_flash.py` は `dry_run=True` で `PyOCDCLI`/`CubeProgrammerCLI` のコマンドを組み立てるだけです。この環境では実機ボードに対しては一切実行していません。何がリリースされたかは `CHANGELOG.md` を参照してください。 シミュレートされたブートローダー（`MockCAN`）はプロトコルの記述から作ったモデルにすぎません。ページ ACK、部分的な最後のページ、読み戻しフレームは再現しますが、本物のブートローダーではないため、テストがすべて成功しても実機での試験の代わりにはなりません（公式の 73476 バイトのイメージがインストールできず、バックアップの最後のフレームが失われていたのに、シミュレーションが本物のブートローダーより寛容だったためにテストは成功していました）。

> **安全性とセキュリティの現状:** このエコシステムは認証された安全システムではなく、実装済みの URTC 基板もまだ存在しません。ブートローダーはファームウェアイメージを CRC32 と共有鍵の HMAC-SHA256 で検査しており、非対称署名ではありません(予定)。公開されているアプリケーションイメージは公開の開発用鍵(`signing_key_kind: dev`)で署名されているため、誰でもブートローダーが受け入れるイメージを作れます。実際の基板には何も送信されていません。ここに書かれた内容を人の安全のために頼る前に、[セキュリティベースライン](https://github.com/JuanenRac/URTC-DOCS/blob/main/docs/SECURITY_BASELINE.md)と[脅威モデル](https://github.com/JuanenRac/URTC-DOCS/blob/main/docs/THREAT_MODEL.md)をお読みください。

## 1. 🔌 アダプターを CAN 通信できるようにする

必要なものはプラットフォームと使用するトランスポートによって異なります：

**Linux、SocketCAN パス（アダプターが対応していれば推奨）：**
アダプター自体に書き込むものは何もありません。起動のたびにインターフェース
を一度立ち上げてください（または永続化するためにネットワーク設定に追加）：
```
sudo modprobe can vcan gs_usb   # gs_usb はほとんどの CANable 系ボードをカバー
sudo ip link set can0 type can bitrate 500000
sudo ip link set can0 up
```
お使いのアダプターが `can0` 以外の名前で列挙される場合は、`ip link show`
（またはプラグインした直後の `dmesg`）で実際の名前を確認してください。
一部のアダプターはネイティブドライバーではなく `slcand` が必要です——
プラグイン後に `ip link show` で CAN インターフェースがまったく表示され
ない場合、これに該当する可能性が高いです。お使いのアダプターのドキュメント
で `slcand` の呼び出し方を確認してください。これにより `slcan0`
インターフェースが作成され、その後は上記と同じ方法で立ち上げます。

**Windows、または Linux でシリアル/SLCAN パスを使う場合：**
CANable Pro v2 はデフォルトで **candleLight** ファームウェアを実行しており、
これはホストとの通信に `gs_usb` プロトコルを使用します——これは Linux の
SocketCAN の `gs_usb` ドライバーがネイティブに期待するのと同じものです
（上記参照）。そのプロトコルはシリアルポートとしては現れ**ません**が、
これはこのパスが必要とするものです。代わりにシリアル/SLCAN を使用するには
（Windows では必須；Linux では任意）：

1. お使いのアダプター向けの SLCAN 互換ファームウェアをダウンロードして
   ください（「canable slcan firmware」で検索——いくつかのメンテナンス
   されているフォークがあります。アダプター自身のドキュメントが指し示す
   ものを使用してください）。
2. アダプターを DFU/ブートローダーモードにします（通常は電源投入中に
   BOOT ボタンを押し続けるか、ジャンパーです——お使いのアダプターの
   ドキュメントを確認してください）。
3. アダプターベンダーのフラッシュツールまたは `dfu-util` を使用して
   SLCAN ファームウェアを書き込みます。
4. 再接続します——今度はシリアルポートとして列挙されるはずです：
   Windows では COM ポート、Linux では `/dev/ttyACM0`/`/dev/ttyUSB0`
   のような形式です。

お使いのアダプターがすでに SLCAN ファームウェアで動作している場合は、
下記のステップ 2 に直接進んでください。

受信した SLCAN の行の実際の長さが、それ自身が宣言した DLC が示唆する
長さと一致しない場合、その後に何が続くかにかかわらず先頭 N 個の 16 進数
文字から解析されるのではなく、不正な形式として扱われスキップされます——
ノイズの多い、または非標準のアダプターに対してデバッグしている場合は
知っておく価値があります。

## 2. 💻 インストールと実行

**Windows：**
```
python -m pip install -r requirements.txt
python urtc_flasher.py
```
または `build_exe.bat` で独立した `.exe` をビルドします（そのファイル
参照）。

**Linux：**
```
python3 -m pip install -r requirements.txt
python3 urtc_flasher.py
```
または `./build_exe.sh`（先に `chmod +x` してください）で独立したバイナリ
をビルドします。

どちらのスクリプトも PyInstaller に `--noconfirm` を渡すため、既存の
`dist/URTC_Flasher` の上に再ビルドすると、スクリプトの出力の中では見逃し
やすい「置き換えますか？」というプロンプトを待つのではなく、直接それを
置き換えます。

### ビジュアル・コマンドデッキ

**Qt Quick** コマンドデッキがこのプログラム唯一のウィンドウです（シミュレーターに対してのみテスト済み。イメージの検証には共有鍵の HMAC-SHA256 を使用します）。次で起動します：
~~~
python urtc_flasher.py
~~~
暗いネイビー/シアンの画面に接続カード、読みやすいファームウェア表、暗い検証ログ、見やすい進捗バーを備え、作業全体をカバーします：メイン基板または拡張スレーブへの CAN-OTA 更新（ターゲットの選択。「基板がアプリケーションを実行中」オプション、F-RAM の消去、ダウングレードの許可はメイン基板のみ）、インストール済みファームウェアの CAN 経由バックアップ、リッスン専用検索付きのバス速度セレクター、GitHub リリースのダウンロード、任意の `.bin` を選ぶファイルピッカー、バス動作の確認、Board Snapshot、4 つのデバイス設定書き込み、読み取り専用の SWD/JTAG 検出、SWD/JTAG によるチップ全体のプログラム（消去/書き込み、ドライラン、消去前のバックアップ、RDP チェック）。基板に書き込む操作はすべて先に確認を求め、ダウングレードの許可はさらに 2 回目の確認を求め、転送中にウィンドウを閉じようとしても再度確認します。実際の基板では何も試していません。`python urtc_flasher.py --cli` はヘッドレスモードです（セクション 7）。

### ヘッダーとツール

- **ヘッダー** - 接続状態、言語セレクター（選択は保存され、次回起動時に適用されます）、バージョン。
- **ログを保存...** と **デバッグバンドルを保存** - 画面のログをプレーンテキストで、またはシステム診断と選択中のファームウェアファイルを含むより詳しい zip を保存します（下の「診断」を参照）。各セッションは `logs/` にも書き込まれ、新しいものが保持されます。
- **URTC Flasher について** - バージョンと作者。**README**（翻訳があればインターフェースの言語で）、**ライセンス**、プロジェクトの **URTC GitHub** ページのボタンがあります。

**言語**：デフォルトは英語です。
ウィンドウ上部の言語セレクターから切り替えます——即座に `urtc_config.json`
に保存され（技術的なハードウェアオーバーライドに使用されるのと同じ
ファイルです——言語設定はそれらと一緒に置かれているだけです）、次回起動
時に適用されます。翻訳は `language/` 下のプレーンテキストファイル
（`english.lng`、`spanish.lng`、`italian.lng`、`french.lng`、
`german.lng`, `japanese.lng`, `chinese.lng`, `portuguese.lng`）として、シンプルな `KEY=Value` ペア、1 行に 1 つの形式で
存在します——`#` で始まる行と空行は無視され、値の中のリテラルな `\n`
は実際の改行になります（数個の複数行ダイアログメッセージで使用されて
います）。URTC-COMMON のカタログから生成されます（翻訳はそこで修正してファイルを書き直し、手では編集しません）。他の言語を追加する際の出発点としても使えます（`language/<name>.lng` を追加し、
`flasher_config.py` の先頭付近の `AVAILABLE_LANGUAGES` に
`("<name>", "現地語名")` を追加し、`urtc_config.json` に
`"language": "<name>"` を設定します）。言語ファイルに存在しないキーは、
クラッシュするのではなく、そのキー自身の名前をそのまま表示するように
フォールバックし、欠落した、または読み取れない言語ファイル（誤った
編集、間違ったファイル名）は、インターフェース全体を英語にフォール
バックします——いずれの場合も、不一致が解決されるまでツールは使用可能な
ままです。

**Linux のシリアル権限：** シリアル/SLCAN パスを使用していて、接続が
「Permission denied」で失敗する場合、ユーザーがシリアルデバイスを所有
するグループに属している必要があります（Debian/Ubuntu では `dialout`；
他のディストリビューションでは異なる場合があります）：
```
sudo usermod -a -G dialout $USER
```
ログアウトして再度ログインし（グループの所属はログイン時に読み込まれ
ます）、再試行してください。本ツールはこの特定のエラーを検出し、
ダイアログで同じ修正方法を表示しますが、事前に知っておく価値があります。
SocketCAN にはこの特定の落とし穴はありません——`can0` のようなインター
フェースへのアクセスは `dialout` グループによって制限されません——
しかし、そもそもインターフェースを立ち上げる（上記のステップ 1）には
`sudo` が必要です。それはネットワークデバイスの設定変更に該当するため
です。

裸の `pip` ではなく `python -m pip`/`python3 -m pip` を使用すると、
両方のプラットフォームで共通の問題を回避できます：`pip` 自身のラッパー
スクリプトは、成功したインストール直後でも必ずしも PATH に含まれている
とは限りませんが、`-m pip` はインストール済みのモジュールを直接見つけ
ます。

## 3. 📁 ファームウェアファイルの配置場所

**フォルダーは空の状態から始まります。** ファームウェアイメージはこのリポジトリには置かれません。[URTC](https://github.com/JuanenRac/URTC) のリリースのアセットです。ウィンドウは選んだリリースからダウンロードし、`python tools/sync_firmware.py` は最新の公式リリース（または `--release TAG`）からフォルダーを埋めます。各ファイルは使用前にリリース署名（`.sig`、Ed25519）とダイジェストで検証されます。公式リリースがまだない間は、GitHub の「latest」が 404 を返すため、代わりに使うリリースを `firmware_release.json` が指定します（現在はベンチ用のプレリリース）。公式リリースが公開されたら、このファイルを削除するかタグを変更してください。

本ツールは、`urtc_flasher.py` のすぐ隣、つまり本リポジトリ自身のルート
に `firmware/` フォルダが存在することを期待します：

```
├── assets/
│   └── URTC_LOGO_FLASHER.svg      <- バナーのソース（ベクター）
├── firmware/
│   ├── URTC_MAIN_FIRMWARE_v<version>.bin  <- 新しい .bin ファイルをここに置く
│   └── URTC_*  <- tools/sync_firmware.py はこのフォルダーの URTC_* ファイルを 1 つのリリースの内容に置き換えます。他のファイルは残ります
├── logs/                          <- 自動作成、セッションごとに 1 ファイル
├── urtc_config.json               <- 任意、デフォルトでは含まれない（下記「HMAC キーの変更」参照）
├── urtc_flasher.py                <- エントリーポイント：CLI 引数と Qt Quick ウィンドウの起動
├── flasher_config.py              <- 設定ファイル I/O、言語読み込み、プロトコル定数
├── flasher_transports.py          <- SLCAN、SocketCAN、MockCAN
├── flasher_swd_tools.py           <- STM32CubeProgrammer / pyOCD ラッパー
├── flasher_validation.py          <- ファームウェアファイル検証（.bin/.hex/.elf）
├── flasher_protocol.py            <- CAN OTA ステートマシン本体
├── flasher_github.py               <- URTC の GitHub リリースのアセットを一覧表示してダウンロード
├── flasher_records.py             <- セッションログ（保存場所・保持）と更新レポート
├── pytest.ini / ruff.toml          <- pytest と ruff（静的チェック）の設定
├── requirements.txt
├── build_exe.bat                  <- Windows 独立ビルド
├── build_exe.sh                   <- Linux 独立ビルド
└── README.md
```

本ツールは可読性のためだけに、上記のモジュールに責務ごとに整理されて
います——それらを別々のファイルとして持つことと、1 つの大きなファイル
として持つこととの間に、機能的な違いはありません。

これは意図的なものです：このリポジトリ全体が自己完結型です。単にボードを
フラッシュしたいだけなら——工場のフロアの PC 上で、USB スティックから、
どこでも——このリポジトリだけを単独でコピーしても、それでも動作します。

**複数の `.bin` を保持できます。** すべてのアプリケーションファームウェア
ファイルがチェックされ、リストに表示されます——ツールは見つけたものを
何でも掴むわけではありません。また、ブートローダーバイナリ（ファイル名に
「BOOTLOADER」を含むもの——`URTC_BOOTLOADER.bin`、
`URTC_SLAVE_BOOTLOADER.bin`）はこのリストから完全にフィルタリングされ
ます。CAN-OTA は常にアプリケーションファームウェアのみをフラッシュする
ためです。ブートローダーの更新には代わりに SWD/JTAG が必要です（下記の
セクション 6）。起動時（および**更新**をクリックするたびに）、
`firmware/` 内の残りの各 `.bin` は、ブートローダー自身が新しいイメージ
に適用するのと同じ妥当性テスト（最初の 4 バイトがこのチップの RAM の
本物の初期スタックポインタのように見える必要があり、サイズがメイン
スロットに収まる必要がある）でチェックされます。各ファイルは、明確な
✓ または ✗ とその理由とともにリストに表示されます：

| ファイル | サイズ | 状態 |
|---|---|---|
| URTC_MAIN_FIRMWARE_v<version>.bin | 71.8 KB | ✓ 有効に見えます |
| URTC_SLAVE_FIRMWARE_v0.1.9.bin | 33.9 KB | ✓ 有効に見えます |
| notes.txt.bin | 0.1 KB | ✗ 最初のワードが有効なスタックポインタに見えません |

- **チェックに合格したファイルが正確に 1 つ** → ツールが起動した瞬間に、
  それがあなたのために選択されます。フォルダに単独で存在する無効な
  ファイルは、他に競合するものがないからといって自動選択される*ことは
  ありません*。
- **有効なファイルが複数** → 何も自動選択されません；リストから希望の
  ものを選んでください。
- **それでも無効に見えるファイルを選択する** → ツールはまず確認を求め
  ます。このチェックは、明らかな間違い（誤ったファイル、途中で切れた
  ダウンロード、空のプレースホルダー）を捕らえるために存在します——
  すべてを捕らえられるわけではありません（破損しているがもっともらしい
  ファイル、または間違ったキーで署名されたファイル）。それこそが、実際の
  転送時のブートローダー自身の CRC32/HMAC チェックの役割です。
- **何も見つからない、またはまったく別の場所にあるファイルが欲しい**
  → **参照 .bin...** ボタンを使用してください。ファイルが実際にどこに
  あるかにかかわらず動作します（そしてどちらの場合も同じ検証チェックを
  実行します）。
- **自分で探し回ることなく最新のビルドが欲しい** → **GitHub から
  ダウンロード...** は、URTC リポジトリの最新 GitHub リリースに添付された
  ファイルを一覧表示します（`github.com/JuanenRac/URTC/releases`——
  ファームウェアのバイナリはリリースのアセットとして公開され、git には
  置かれません）。あなた自身のローカルの `firmware/` フォルダへ直接
  ダウンロードするものを選べ、再起動不要で、他のファイルと同様に上記の
  リストに表示されます。ウィンドウ上部の入力欄にリリースタグ（例：
  `v0.3.5`）を入力して **読み込み** を押すと、最新以外のリリースを一覧
  表示できます。イメージの `.sha256` と `.manifest.json` は一緒に
  ダウンロードされます。GitHub 自身のホスト（`github.com` と、そこから
  リダイレクトされるアセット保存用ホスト）のファイルだけが受け入れられ、
  リリースが示すサイズと異なるファイルは破棄されます。GitHub 自身の
  公開 API を使用します（未認証のため、短時間で多用すると 1 時間あたり
  60 リクエストのレート制限に達する可能性があります。環境変数
  `GITHUB_TOKEN` を設定すると上限が上がります）——ここでは GitHub
  アカウントは必要ありません。

公式リリースの各ファイルにはリリース署名（`<ファイル>.sig`、Ed25519）があります。フラッシャーは署名がある場合に検証し、不正な署名は拒否します。ベンチ用プレリリースのように署名のないセットは、`tools/sync_firmware.py` では `--allow-unsigned` を付けた場合にのみ受け付けられます。

**各ファームウェアファイルの隣に置かれる `<filename>.manifest.json` と
`<filename>.sha256`**——URTC のビルドが各イメージについて公開します（GitHub
からイメージと一緒にダウンロードされます）。マニフェストにはバージョン、
`sha256`、アプリケーションイメージの場合はブートローダーが期待する
`hmac_sha256` の値（共有鍵の HMAC-SHA256 であり非対称署名ではありません。`signing_key_kind: dev` は公開の開発用鍵を示します）が含まれます：

```json
{"component": "main_application", "version": "<version>", "sha256": "b48d4cd5...", "hmac_sha256": "b63a701e...", "signing_key_kind": "dev"}
```

両方のダイジェストは書き込み直前に確認され、不一致の場合はバス上に何も
送信する前に**書き込みを拒否**します（誤ったファイル、破損したダウンロード、
古いマニフェスト）。ブートローダーには公開された署名が送られ、マニフェストの
バージョンが報告されます。マニフェストのないファイル（自作ビルド）は、
`urtc_config.json` に署名鍵が設定されている場合のみ書き込まれます——下記の
HMAC キーの変更を参照してください。

後で新しいビルドを追加する：単に `firmware/` に投入して**更新**を
クリックするだけです——再起動は不要です。

## 4. 🔍 現在インストールされているものの確認

> Qt Quick デッキでは、両方のトランスポートのポート（シリアルアダプターと、Linux では SocketCAN インターフェース）が 1 つのリストにまとまっており、このセクションの問い合わせは **ボード状態を読む** が行います。バージョン、CAN エラーカウンター、拡張基板の種類、MLX9064x のバリアント、周辺機器情報をまとめて問い合わせ、ボードスナップショットに表示します。デバイス設定セクションの保存は値を書き込みます。

Linux 上で SocketCAN が利用可能な場合、上部に**トランスポート**の選択肢
が表示されます——接続する前にシリアル/SLCAN か SocketCAN を選んで
ください。Windows ではこの行はまったく表示されません；シリアル/SLCAN
が唯一の選択肢です。

**接続**をクリックすると、ツールは自動的にボードに現在何が動作している
かを尋ねます（CAN ID `0x7F8` → `0x7F9`——`docs/CANBUS.TXT` 参照）。これは、
ボードが通常どおりアプリケーションを実行している場合*でも*、ブート
ローダー内に留まっている場合*でも*動作するため、それを確認するためだけ
にリセットをトリガーする必要はありません。その後いつでも**照会**を
クリックして再確認できます（フラッシュ完了直後に、新しいバージョンが
実際に反映されたことを確認するのに便利です）。

**ブートローダー自体が応答する場合**（アプリケーションを実行しておらず、
ブートローダー内にとどまっているボード）、それは自身のバージョンも
報告します——これはインストール済みアプリケーションのバージョンとは
別のもので、`bootloader_common.h` 内の自身の
`BOOTLOADER_VERSION_MAJOR/MINOR/PATCH` を通じて追跡され、`0x7F9` の
すぐ隣に 2 つ目のフレーム（`0x7FA`）として送信されます。実行中の
アプリケーションはこれを決して送信しません——それはブートローダー自身に
尋ねる以外に、現在フラッシュされているブートローダーのバージョンを
知る方法がないため、これはボードが実際にそこにいるとき（`0x7F0` の
直後、またはアプリケーションへジャンプする前の新しい起動時）にのみ
表示されます。

**パッチ番号。** ファームウェア 0.3.5 以降のボードは、インストール済み
アプリケーションのパッチ番号も送信します（フレーム `0x7E9`、`0x7F9` の
直後）。そのためウィンドウとログには `メジャー.マイナー` ではなく
`メジャー.マイナー.パッチ` の完全な形（例：`v0.3.5`）が表示されます。
イメージのパッチは、そのマニフェストのバージョンの 3 番目の部分です。
更新前、ログは「インストール済み -> 新規」をこの形式で表示し、パッチは
双方が持っている場合にだけ「インストール済みより古い」警告に使われます。
パッチ番号に対応していない古いボードはそれなしで応答し、従来とまったく
同じ表示になります。ブートローダーが（同じフレームのフラグで）パッチを
読むと通知した場合、更新終了フレームはマイナーフィールドの上位バイトに
パッチを載せます。それ以外のブートローダー、およびパッチのない
イメージには、従来どおり 2 つの数値のフレームが送られます。拡張スレーブの
バージョン応答（`0x218`）にも同じオプション拡張があります。これは
プロトコル記述に従ったもので、シミュレーターでのみテストされており、
実機では試していません。

表示されるもの：

- **`v0.2（アプリケーション、HardwareID 0x0303CC01）`** —— 通常のケース、
  アプリケーションが実行中で、すべてが一致しています。
- **`ブートローダーが実行中、有効なファームウェアが現在インストール
  されていません、ブートローダー v0.1.2`** —— ボードは、ジャンプ先の
  ないブートローダーに閉じ込められています（空のチップ、またはメイン
  スロットのすべてのチェックが失敗しました）。これはまさに本ツールが
  修正するために存在する状況です——フラッシュしてください。ここに表示
  されるブートローダーバージョンはブートローダー自体のものであり、
  チェックに失敗したどのアプリケーションバージョンとも無関係です。
- **赤で表示される `⚠ HardwareID mismatch!`** —— 何かが応答しましたが、
  その HardwareID が本ツールが期待するものと一致しません。まず理由を
  理解せずにフラッシュしないでください；いずれにせよブートローダーは
  更新を拒否しますが、ここでの不一致は、あなたが完全に間違ったボードを
  指している可能性も意味します。
- **応答なし**（赤）—— ボードが無応答、ビットレートが間違っている、
  または実際には接続されていません。物理的な接続、そして SocketCAN
  パスの場合は、インターフェースが実際にアップしているか確認してくだ
  さい（`ip link show`）。

**拡張ボード：** バージョンチェックのすぐ下にある、独立したドロップ
ダウンと照会/保存のペア。CAN 経由（`0x1A0`/`0x1A1`）で、7 つの可能な
`CONN_EXPANSION` 構成（なし、または 6 つの実際のバリエーションのいずれか
——`EXPANSION.TXT` 参照）のうちどれが物理的に取り付けられているかを読み
書きします。ボードにはこれを自ら感知する電気的な方法がないため、伝えて
やる必要があります——これは（`URTC Tester` だけでなく）ここにも存在し
ます。これは、ファームウェア更新と一緒に行うのが最も自然な、一度限りの
ハードウェア構成ステップだからです。**保存**は、明示的に再び変更される
まで電源サイクルをまたいで持続するため、まず確認を求めます。

**MLX9064x センサーバリアント：** そのすぐ上にある拡張ボードコントロール
と同じ形——CAN 経由（`0x1A6`/`0x1A7`——`CANBUS.TXT` 参照）で、3 つの
MLX9064x 系サーマルセンサー（またはまったくなし）のうちどれが実際に
搭載されているかを読み書きするドロップダウンと照会/保存のペアです。
上記の拡張ボードが Advanced バリアントまたは Basic+MLX9064x に設定されて
いる場合にのみ意味を持ちます；ボード自身のファームウェアは、他のすべての
拡張ボードタイプではこの設定を完全に無視します。「未搭載」（安全な
デフォルト）は、意図的に MLX90640 を想定することにフォールバックしません
——実際に MLX90640 が配線されたボードは、拡張ボードタイプ自体と同様、
これを明示的に一度設定する必要があります。

## 5. ⚡ フラッシュ

1. **接続**：シリアル/SLCAN または SocketCAN（Linux のみ）を選び、
   次にポート/インターフェースを選び、次に接続をクリックします。
   シリアル/SLCAN の場合、これは 500 kbit/s（URTC の固定バス速度）で
   CAN チャンネルを開きます；SocketCAN の場合、インターフェースはすでに
   そのビットレートになっていることが期待されます（上記のステップ 1）
   ——本ツールはそれを設定しません。いずれの場合も、現在のバージョンが
   自動的に照会されます——上記のセクション 4 を参照。
2. **フラッシュ対象を選ぶ**：「このボード（メイン）」または「拡張
   スレーブ」——デフォルトはメインボードで、はるかに一般的なケースです。
   スレーブオプションは、Advanced 拡張ボードバリアント
   （TMC2209+STM32F303CBT6 または TMC5160A+STM32F303CBT6）上の何かに
   しか到達しません——その更新は、別個の物理接続ではなく、メインボード
   自身の I2C ブリッジ（`CANBUS.TXT` 自身の `0x210`-`0x219`）を通じて
   中継されます。「フラッシュ前に F-RAM を消去」（下記のステップ 4）は、
   スレーブが選択されると自動的に無効になります——スレーブチップには
   消去すべき独自の F-RAM がありません。
3. **ファームウェアを選択**：検出されたリストから選ぶか、参照します——
   検出と検証の正確な仕組みは上記のセクション 3 を参照してください。
4. **フラッシュ**：
   - ボードが電源投入され、正常に動作している場合は、「ボードは現在
     アプリケーションを実行中」をチェックしたままにしてください——
     ツールはまず `0x7F0` マジックペイロードトリガー（またはスレーブが
     選択されたターゲットの場合は `0x210`、スレーブへ中継）を送信し、
     これはブートローダーへリセットする前に、すべてのアクチュエータを
     安全にシャットダウンします。
   - ボードがすでにブートローダー内にある場合（新しい JTAG フラッシュ
     直後、または上記のバージョンチェックが「有効なファームウェアが
     現在インストールされていません」と表示した場合）は、チェックを
     外してください。
   - **ファームウェアをフラッシュ**をクリックして確認します——確認
     ダイアログには、これからフラッシュしようとしているターゲットの
     名前が示されるので、実際に選択したかったものと一致しているか
     再確認してください。ログはすべてのプロトコルステップを表示し、
     進捗バーは転送中はページごとの書き込み進捗を、その後は最終的な
     バックアップからメインへのコピー中はコピーの進捗を追跡します。

いずれかの時点で検証が失敗した場合（CRC32、HMAC、または HardwareID の
不一致）、ブートローダーのメインスロットは決して触れられません——ボード
は、すでに持っていたどんなファームウェアでも、そのまま動作し続けます。
再試行はいつでも安全です。

**ファームウェアをバックアップ（CAN）**：現在インストールされている
ファームウェアを、無変更のままバスを通じて読み戻し、`.bin` ファイルとして
保存します——SWD セクション自身の「消去前にフラッシュ全体をバックアップ」
（下記のセクション 6）の CAN 版に相当します。それを生成したファイルを
まだ持っていない場合、後で今日の正確なバイトを取り戻す唯一の方法である
ため、あらゆる更新の前に、特に意図的なダウングレード（下記）の前に行う
価値があります。メインボードのみ対応、かつボードが実際にブートローダー
内にあるときのみ——`0x7FE`/`0x7FF` を実装したブートローダーが必要です
（`docs/CANBUS.TXT` 参照）；古いものは単に応答せず、静かに空のファイル
になるのではなく、明確なタイムアウトとして表れます。 実際には、このバックアップは有効なアプリケーションがないボード、または更新の途中で止まったボードで機能します。有効なアプリケーションがある場合、更新開始フレーム（`0x7F1`）が届かない限りブートローダーはリセットの約 600 ms 後にそちらへジャンプし、このツールにはブートローダーを待機させ続けるボタンがありません（ブートローダーの変更が必要になります）。通常どおり動作しているボードでは、代わりに SWD/JTAG（セクション 6）でフラッシュをバックアップしてください。

**バージョンと署名のヒント**：転送の前にツールはボードにインストール済みの内容を問い合わせ、「インストール済み vX.Y -> 新規 vA.B」とログに記録します。新しいバージョンのほうが古い場合は、ダウングレードを許可しない限りブートローダーが拒否することを警告し、先にバックアップを取るよう提案します。マニフェストが「公開の開発用鍵で署名済み」と示すイメージ（同梱の公式イメージがそうです）には、ファイル名の下に赤い警告が表示されます。`urtc_config.json` に `"require_production_signature": true` を設定すると、そのようなイメージを完全に拒否します。ボードが有効なファームウェアのないブートローダーから応答した場合は、`firmware/` にある最新の公式メインボード用イメージが選択され、確認して書き込むことができます。更新が成功するたびに小さなレポート（`logs/urtc_update_report_*.json`：ツールのバージョン、オペレーター、イメージ名・サイズ・SHA-256、更新前後のバージョン）が書き込まれます。レポートは自身の SHA-256 を持つため編集に気付けますが、署名ではありません。

**意図的に古いバージョンをインストールする**：ブートローダーは通常、
すでにインストールされているものより古いバージョンを宣言する、有効に
署名されたイメージを拒否します（検証失敗理由「rollback rejected」）——
これは、既知の脆弱性があるバージョンが再送されるのを防ぎます。信頼
できる、より古いリリースへ本当に戻す必要がある場合は、フラッシュ前に
**「この更新についてダウングレードを許可（防ロールバックを回避）」**
（ターゲット：メインボードのみ）をチェックしてください——これは意図的
に安全チェックを回避するため、2 番目の確認ダイアログが表示されます。
これでも完全な古いイメージが通常の転送を通じてアップロードされます。
それはその 1 回の試行についてのみバージョン順序チェックを解除するだけ
です（`0x7FD`——`docs/CANBUS.TXT` 参照）；ボードへ報告されるバージョン
番号は、それが存在する場合はファイル自身の隣にある `.manifest.json`
から取得され（上記のセクション 3 参照）、そうでなければ本ツール自身の
現在設定されているバージョンにフォールバックし、いずれの場合も明確に
ログに記録されるため、それが静かな推測になることは決してありません。

## 6. 🛠️ SWD/JTAG 経由でチップ全体をプログラムする（上級者向け）

**SWD/JTAG プログラミング**タブの「SWD/JTAG 経由でチップ全体をプログラム
（上級者向け）」パネルは、完全な立ち上げフラッシュを行います——チップ
全体を一括消去し、その後、**ターゲットチップ**の選択（下記参照）に対応
する、そのチップ自身の実際のアドレスに、ブートローダーとアプリケーション
の両方のイメージを新規に書き込みます。これは上記のセクション 1-5 とは
**異なる種類の操作**です：

|  | CAN OTA 更新（セクション 1-5） | 完全チップ SWD/JTAG（セクション 6） |
|---|---|---|
| 中断時の自己修復 | あり——ゴールデンイメージのバックアップスロットが実行中のファームウェアの生存を保証 | なし——再プログラムされるまで何も実行しない |
| 復旧可能性 | 自動、操作不要 | 可能——再接続して SWD 経由で再度フラッシュするだけ；デバッグポートはフラッシュ内容に依存しない。真の永久的なロックアウト（RDP2 オプションバイト）だけがこれを妨げ、本ツールはオプションバイトを設定しない |
| ブートローダーへの影響 | なし | あり、設計上 |
| 必要なもの | USB-CAN アダプター | SWD/JTAG プローブ（ST-Link またはそれに類するもの） |
| 一般的な用途 | 日常的なファームウェア更新 | 空のチップの初回立ち上げ、またはブリックしたボードの復旧 |

**ターゲットチップ：** 「このボード（メイン）」または「拡張スレーブ」——
CAN-OTA タブ自身のセレクターと同じ 2 つの選択肢ですが、ここでは本当に
独立した選択です：SWD/JTAG は、これが設定されているどちらのチップにも
プローブが物理的に接続されている必要があります。CAN-OTA とは異なり、
1 つの接続で両方に到達できるブリッジは存在しないためです。これを切り替え
ると、使用するフラッシュアドレスが自動的に変更されます：

| | メインボード（STM32F303CC） | 拡張スレーブ（STM32F303CBT6） |
|---|---|---|
| ブートローダーアドレス | `0x08000000`（32K 領域） | `0x08000000`（18K 領域） |
| アプリケーションアドレス | `0x08008000`（112K 領域） | `0x08005000`（54K 領域） |
| pyOCD ターゲット文字列 | `stm32f303cc` | `stm32f303cb` |

上記の両方のターゲット文字列は、本プロジェクト自身が各チップの実際の
pyOCD ターゲット名に対して行った最善の推測であり、これが書かれている
時点で稼働中の pyOCD インストールに対して確認されたものではありません
（pyOCD における STM32 のカバレッジは、組み込みターゲットよりも主に
CMSIS-Pack を通じて提供されます）——「target not found」のようなエラーで
フラッシュが失敗する場合は、自分で `pyocd list --targets --name
stm32f303` を実行してください。`pyocd pack install <実際の名前>` で
正しい CMSIS-Pack が取得されます。

**以下のいずれかが必要です**（ツールは利用可能な方を自動検出し、見つけた
ものだけを有効化します）：
- **pyOCD** —— `pip install pyocd`。無料、オープンソースで、pip パッケージ
  以外に個別のインストールは不要です。
- **STM32CubeProgrammer** —— ST の公式ツールで、[st.com](https://www.st.com)
  から個別にインストールします。他の STM32 作業のためにすでにお持ちの
  場合、ここで追加のインストールは不要です。

どちらも Python ライブラリとしてインポートされるのではなく、コマンド
ライン子プロセスとして駆動されます——実行前にログに正確なコマンドが
記録されるのが確認できます。

**ファイル形式：** `.bin`（本ツールがすでに知っている固定アドレスが
必要——自分で入力する必要はありません）または `.hex`（自身のアドレスを
携え、そのまま使用されます）。混在も問題ありません——ブートローダーは
`.hex`、アプリケーションは `.bin`、あるいはその逆、どちらも動作します。
両方のファイルピッカーは、続行を許可する前に、選択したファイルを検証
します（ターゲットスロットに対して妥当なサイズか、そしてフォーマットが
自信を持ってチェックできる場合には妥当な初期スタックポインタか）。
CAN パスのファームウェアピッカーがすでに行っていたのと同じ方法です。

**破壊的な処理が実行される前に接続がチェックされます**。単にエラーが
ないことではなく、実際のプローブ/ターゲットの**積極的な証拠**が要求
されます——STM32CubeProgrammer 自身の終了コードだけでは信頼できる成功/
失敗の合図にはならないため、専用の接続チェック（`pyocd list --probes`、
または STM32CubeProgrammer 向けの接続のみの `-c port=SWD`）が、一括
消去ステップが実行される前に実行されます。その後のすべてのコマンドの
出力も、他の状況でツールの終了コードだけが信頼できない場合に備えて、
第 2 層として既知の失敗テキストがスクリーニングされます。

**ドライランはデフォルトでオンです。** 最初は、それをチェックしたまま
「チップ全体をフラッシュ」を押してください——それは、ボードに一切触れる
ことなく、正確なコマンドをログに出力します。それらを読み、パスと
アドレスが正しいことを確認し、*その後*ドライランのチェックを外して、
本当に実行してください。

**「消去前にフラッシュ全体をバックアップ」**は、まず同じツール自身の
メモリ読み取りからファイルへのコマンド（STM32CubeProgrammer では `-r`、
pyOCD では `commander savemem`）を通じて、256KB のフラッシュ領域全体を
`.bin` ファイルへ読み取ります——ここでは本当の保険です。CAN OTA 更新
（ゴールデンイメージのバックアップスロットがすでに保護しています）とは
異なり、チップ全体の消去には他に元に戻す手段がないためです。デフォルト
ではオフです。10-30 秒が追加され、空の/新しいチップでは不要だからです；
すでに何かが動作しているボードを上書きする前にチェックする価値があり
ます。読み取りが実際にファイルを生成しなかった場合、消去は、あなたが
要求したバックアップなしに進むのではなく、拒否されます。

**テスト状況：** 上記の接続チェックロジックは、実際の STM32CubeProgrammer
の出力（本物の成功した接続ログと、文書化された「No target connected」
の失敗の両方、どちらも ST 自身のコミュニティフォーラムから入手）、
そして実際のユーザーが遭遇した正確な偽の成功シナリオに対して検証
されています。実際の ST-Link と実際の STM32F303CC に対する完全な消去/
プログラム/検証のシーケンスは、まだエンドツーエンドで実行されていません
——これを書いた環境には USB アクセスがありません。最初の実際の完全な
試行には適切な注意を払ってください——もしあれば、まず予備/テストボード
で試し、あなたの特定の pyOCD バージョンやプローブがここで想定している
ものと一致しない場合に備えて、フォールバックプラン（STM32CubeIDE 自身の
フラッシュツール、または `st-flash`）を念頭に置いておいてください。

## 7. ⌨️ CLI モード（ヘッドレス、GUI なし）

ディスプレイのない CI パイプライン、テストベンチ、または生産ライン
スクリプティング向け：

```
python3 urtc_flasher.py --cli --port /dev/ttyACM0 --file firmware.bin
```

```
usage: urtc_flasher.py --cli [-h] [--transport {serial,socketcan,python-can,mock}] --port PORT
                             --file FILE [--no-trigger] [--force]
```

終了コード：`0` 成功、`1` プロトコル/接続エラー、`2` 引数が不正、
またはファームウェアファイルが検証に失敗（`--force` を渡すとそれでも
フラッシュします）、`130` Ctrl+C でキャンセル。CAN OTA 更新パス
（セクション 1-3）のみをカバーします——SWD/JTAG の完全チップパスは、
誰も見ていない状態でスクリプト化された実行が誤ったファイル/ターゲットの
組み合わせを間違えた場合にどれだけ多くのものが危険にさらされるかを考慮
し、現時点では意図的に GUI 専用です。

**`--transport python-can`** は、オプションの `python-can` パッケージ（`pip install python-can`）を使って PCAN、Kvaser、gs_usb/candleLight などの対応インターフェースを扱うため、アダプターを SLCAN に書き換える必要がありません。`--port` は `<インターフェース>:<チャンネル>`（例：`pcan:PCAN_USBBUS1`）となり、バスは 500 kbit/s で開かれます。コマンドラインでのみ利用できます。

**`--transport mock`** は、実際のボードではなく、シミュレートされた
メモリ内ブートローダーに対して更新シーケンス全体を実行します——アダプター
もポートも、物理的なものは何も関与しません：

```
python3 urtc_flasher.py --cli --transport mock --file firmware.bin --no-trigger
```

CI パイプラインで、または実際のハードウェアに触れる前に、本ツール自身の
ロジック（リトライ動作、タイムアウト処理、終了コード）をテストするのに
便利です——実際のボードとは通信しません。`--mock-fail 0x03`（または
`docs/CANBUS.TXT` の他の任意の `VERIFY_FAIL_REASON_*` 値）は、シミュレー
トされた更新を成功ではなく検証失敗にし、同じ方法で失敗パスをテストでき
るようにします。

## 8. 🔄 CAN 更新中の信頼性、およびセッションログ

CAN 更新中に、あるページの ACK が通常の 3 秒のウィンドウ内に到着しない
場合、ツールは諦める前に、短いバックオフを挟んで最大 2 回まで再び待機
します（ページのデータは再送信しません）。これは単に遅れているだけの ACK
にしか効果がありません：ブートローダーは各ページの ACK を一度だけ送信し、
繰り返すことはないため、本当に失われた ACK は回復できず、更新はエラーで
中止されます（ボードはブートローダーに留まり、更新はそのままやり直せます）。
タイムアウト時にページデータを再送信することは意図的にありません——データ
が問題なく届いていた場合、再送信はブートローダーにそれらのバイトを*次の*
ページの先頭として読み取らせ、転送を同期不能にしてしまうためです。待機中、
ブートローダー自身のハートビート（おおよそ 1 秒ごとに送信）をそのページが
示唆する進捗と比較し、一致した場合はログに記録します；ハートビートは整数の
パーセント値なので、これはあくまでヒントであり、ページが到着した証拠では
なく、結果を変えることもありません。

各セッションはまた、画面上のログとは独立して、`logs/`
（`urtc_flasher_YYYYMMDD_HHMMSS.log`）へタイムスタンプ付きのログ
ファイルを書き込みます——現場で何か問題が発生した場合、ファームウェアを
書いた人へ完全なトレースを渡すのに便利です。このフォルダは自動的に
作成され、削除しても安全です；古いログを読み戻すものは何もありません。 保持されるのは最新の 30 件のセッションログだけです。プログラムの隣のフォルダーに書き込めない場合（読み取り専用のインストール）は、代わりにユーザーごとのフォルダーが使われます（Windows では `%LOCALAPPDATA%\URTC-Flasher\logs`、それ以外では `~/.local/state/urtc-flasher/logs`）。

## 9. 📊 診断——バスアクティビティ、ビットレート、デバッグバンドル

**ビットレートセレクター + 自動検出**（シリアル/SLCAN のみ）：URTC の
バスは 500 kbit/s に固定されており、これがデフォルトのままです——これは、
誤って設定されたアダプター、または非標準のボードのトラブルシューティング
のためのものです。**自動検出**は*待ち受けるだけ*です：SLCAN のリッスン
オンリーモード（`L`）でアダプターを開き、各標準ビットレートを順に試して、
有効な CAN フレームが聞こえた最初のもので停止します。したがって送信は
一切行わず、稼働中のバスを乱すことはありません。そのため他のノードが送信
している必要があり、アダプターがリッスンオンリーモードに対応している
必要があります；バスが静かな場合（またはそのモードがないアダプターの場合）
は何も見つからないので、ビットレートを手動で選択してください。クリック
した時点ではまだ接続されていません。SocketCAN のビットレートは OS レベル
（`ip link`）で設定されるため、そのトランスポートではこのコントロールは
無効化されます——ここには試すものがありません。

**バスアクティビティ**（照会の隣にある「チェック（2秒）」）：接続されて
いるどちらのトランスポートでも、固定の 2 秒ウィンドウ内で実際に見られた
実際のプロトコルフレームをカウントします。これは意図的に、真の CAN
バス負荷率とは**異なります**——それには netlink クエリ（SocketCAN）や
アダプター固有の拡張機能（SLCAN）が必要ですが、本ツールには*アダプター
自身*のコントローラーに対してそれを取得するための標準的な、依存関係
なしの方法がありません。それが実際に提供するのは：どちらのトランス
ポートでも、「このバス上で何かが通信しているか、大まかにどのくらいの
頻度で」という本物の、直接測定された信号です。特に SocketCAN の場合、
Linux 自身のインターフェース統計情報（`/sys/class/net/<iface>/statistics/`）
の 2 秒の差分も表示します——すべてのインターフェースが公開している
基本的な rx/tx/error/drop カウンター、プレーンなファイルとして読み込ま
れ、追加の依存関係はありません。SocketCAN 経由での接続はまた、すべての
Linux インターフェースが公開しているプレーンな 0/1 のファイルである
`/sys/class/net/<iface>/carrier` も読み取ります。CAN コントローラーが
バスオフになると、カーネルドライバーは `netif_carrier_off()` を呼び
出すため、ここでの「キャリアなし」はバスオフ、または同様の死んだリンク
の実質的な証拠であり、正確な復旧コマンド
（`sudo ip link set <iface> down && sudo ip link set <iface> up type can
bitrate 500000 restart-ms 100`）とともに警告として記録されます。本
ツール自体はそのコマンドを実行しません——本物のバスオフをクリアする
には、カーネルレベルでインターフェースをダウンさせてから再度アップ
させる必要があり、それには root 権限が必要で、システムのネットワーク
構成を変更することに該当します。あなたに代わって黙って行うようなこと
ではありません。

**エラーカウンター（TEC/REC）**（バスアクティビティの隣）：上記の
アダプター側のカウンターとは異なり、これは**ボード自体**に、自身の
CAN コントローラーの送信/受信エラーカウンター（`0x7FB`/`0x7FC`——
`docs/CANBUS.TXT` 参照）を尋ねます。現在実行中のアプリケーションまたは
ブートローダーのどちらかが応答します。緑色は両方のカウンターが 0
（エラーアクティブ、健全）であることを意味します；オレンジ色は一方または
両方が非ゼロだが 128 未満（依然としてエラーアクティブですが、何かが
再送信を引き起こしています）であることを意味します；赤色は 128 以上
（エラーパッシブまたはそれ以上）、または応答がまったくない（`0x7FB`
をまだ実装していない古いファームウェア/ブートローダー、またはボードが
接続されていない）ことを意味します。TEC が着実に上昇し REC が横ばいで
ある場合、通常はこのボード自身の送信が確認されていないことを示します
——バス上に他のノードがない、またはこのボード自身の接続に特有の配線/
終端/ビットレートの問題です。

**デバッグバンドルをエクスポート**（ログの上）：現在の画面上のログ、
基本的なシステム診断情報（OS、Python バージョン、見つかったツール、
現在のトランスポート/ポート/ビットレート）、そして現在選択されている
CAN ファームウェアファイルを `.zip` として保存します——現場で何か問題が
発生した場合、ログテキストを手動でコピーする代わりに、完全な状況を
ファームウェアを書いた人へ渡すのに便利です。

## 10. 🔬 SWD/JTAG——ファイル形式、スロット検証、プローブ選択

**ファイル形式**：SWD セクションのブートローダー/アプリケーションピッ
カーは `.bin`、`.hex`、`.elf`/`.axf` を受け付けます。ELF/AXF は、少量
の手書きの構造体アンパック（ELF ヘッダー + プログラムヘッダーのみ——
シンボルなし、セクションヘッダーなし）で解析されます。意図的に
`pyelftools` は使用していません：本プロジェクトは非標準ライブラリへの
依存をゼロに保っており、完全な ELF パースは、この特定の妥当性チェック
が必要とする以上のものです。本プロジェクト自身のビルドから実際にコンパ
イルされた `BOOTLOADER.elf`/`APP.elf` に対して検証済みです——どちらも、
合成テストファイルだけでなく、実際のロードアドレス
（`0x08000000`/`0x08008000`）で正しく検証されます。32 ビットリトル
エンディアン ARM のみで、これは Cortex-M ターゲットが常にそうである
ものです。`.hex` ファイルが宣言するサイズは、その最低から最高の
レコードまでのアドレス範囲ではなく、実際に占有されているバイト数です
——そのため、スパースなファイル（実際のファームウェアの小さなブロック
と、離れた独立したオプションバイトまたはキャリブレーションデータの
ブロック、一部の STM32 ツールチェーンは 1 回のエクスポートにこれらを
まとめます）は、その間のギャップではなく、実際のコンテンツに基づいて
検証されます。`.bin` 以外の拡張子（`.img`、`.rom`、または拡張子が
まったくない——ファイルピッカーの「すべてのファイル」オプションで
選択可能）の生のファームウェアイメージは、`.bin` と同様に、それをどの
スロットに読み込んでいるかからベースアドレスを取得します。

**ブートローダー/アプリケーションスロット検証**：ファイルピッカーは、
各イメージが、それが置かれようとしているスロットにふさわしいことを
検証します。単に*何らかの*有効なファームウェアのように見えるという
だけではありません。ブートローダーイメージとアプリケーションイメージは
どちらも、同じくらい妥当なスタックポインタを持ちます——同じチップ、
同じ RAM——そのため、一方が他方のスロットに入ってしまった場合、その
チェックだけでは区別できません。区別できるのは：リンクされたイメージの
**リセットハンドラー**は、リンク時に焼き込まれた実際の、絶対的な
アドレスであり、それが実際にリンクされた領域の内側だけを常に指す
ということです。本プロジェクト自身の実際にコンパイルされた
`BOOTLOADER.bin`/`APP.bin` に対して検証済みです：それらのリセット
ハンドラーはそれぞれ `0x08000785` と `0x0800C0CD` であり、それぞれ
自身のスロットのアドレス範囲内に正しく収まり、もう一方の範囲外にあり
ます——そのため、どちらかを間違ったスロットに入れると、静かに受け入れ
られるのではなく、捕捉されブロックされます。`.hex`/`.elf` にも同じ
ロジックが適用され、代わりにそれら自身の埋め込まれたロードアドレス
に対してチェックされます。

**オプションバイトをチェック**（同じ SWD/JTAG プログラミングタブ、
STM32CubeProgrammer のみ——pyOCD は CLI 経由でこれを同じ方法では公開
していません）：読み取り専用の `-ob displ` ダンプで、消去/書き込みは
ありません。本ツール全体が SWD リスクに対して払っているのと同じ注意
をもって RDP レベルにフラグを立てます：
- **RDP0** —— 保護なし、開発ボードとしては正常。
- **RDP1** —— CubeProgrammer の Read Unprotect で可逆ですが、それは
  保護を解除する過程の一部としてチップを一括消去します——本ツールが
  これを自動的に行うことはありません。
- **RDP2** —— このプロジェクト全体で唯一、本当に**永久的**な
  ロックアウトです。上記で文書化された他のすべてのリスク（すべて SWD
  経由で回復可能）とは異なり、RDP2 は ST 自身の設計によりデバッグ
  ポートを永久に無効化します。このチェックは、完全チップ操作の前に、
  後ではなく、それを捕らえるために存在します。

**プローブ選択**（同じタブ）：複数の ST-Link/プローブが同時に接続されて
いる場合、すべてのコマンドは、プローブのドロップダウンから明示的に
1 つを選ぶことを要求します——「OS がたまたま最初に列挙したもの」という
ことはありません。ちょうど 1 つのプローブが接続されている場合は自動
選択されます；0 個または複数の場合は、更新を押して選択してください。
これは、完全チップフラッシュとオプションバイトチェックの両方に適用
されます。どちらも、複数デバイスのベンチで間違ったボードを推測する
ことが実質的なリスクとなるほど、破壊的操作に近いためです。

**pyOCD の書き込みは、終了コードを単に信頼するのではなく、明示的な
読み戻しで検証されます。** pyOCD 自身の `flash` コマンドは、すでに
一致しているページの再書き込みをスキップします（速度の最適化であり、
検証レポートではありません）。そのため、本ツールは書き込み後に、
STM32CubeProgrammer の `-v` フラグがすでに行っているのと一致する、
本物のバイト単位のチェックとして、両方のイメージに対して
`commander compare` ステップを追加します。`.bin` のみが対象です：
`compare` はフラッシュの内容をファイルの生のバイトと比較しますが、
これは成功したフラッシュの後でも `.hex`/`.elf` ファイル自身のエンコー
ディングとは正しく一致しないため、これら 2 つのフォーマットはこの特定
のステップをスキップし、代わりに pyOCD 自身の内部の書き込み時検証に
依存します。

## 11. 📡 転送テレメトリと詳細な検証失敗理由

**転送テレメトリ**：ログは、CAN 更新中のページごとの実効 KB/s と経過
時間、そして最後の要約行（合計時間、平均 KB/s、何回のページ ACK 再試行
が発生したか）を表示します。純粋に情報提供のためのものです——フラッシュ
の動作を変更するわけではなく、単に「これは単に遅いだけ」なのか「実際に
何かが間違っている」のかを一目で区別しやすくするだけです。

**具体的な検証失敗理由**：CAN 更新中に検証が失敗した場合、
`bootloader_protocol.c` はステータス `0x05`（検証失敗）とともに理由
バイトを送信します——転送不完全、CRC32 不一致、HMAC 不一致、または
HardwareID 不一致であり、すべての失敗が同じに見えるわけではありません。
正確なフレーム形式は `docs/CANBUS.TXT`（`0x7F5`、この特定のステータス
では DLC 2）を参照してください。本ツールとブートローダーはこのフレーム
形式について合意しているため、異なるバージョンのプロトコルを持つカスタム
ブートローダーを構築している場合は、両方を一緒にフラッシュしてください。

**拡張スレーブについても同じ詳細**：失敗したスレーブ更新（ターゲット：
「拡張スレーブ」）は、`0x215` が `STATUS_VERIFY_FAIL` を報告した直後に
`0x219` を照会し、スレーブブートローダー自身の
`REG_VERIFY_FAIL_REASON` を中継します——上記と同じ 5 つの理由ですが、
CAN フレームから直接読み取るのではなく、I2C ブリッジ経由で到達します。
`0x219` を実装したスレーブブートローダーが必要です（本ツール自身のこれ
へのサポートと同時に追加されました）；古いスレーブブートローダーは単に
その照会に応答せず、本ツールは代わりに汎用の「検証失敗」メッセージに
フォールバックします。

## 12. 🧹 フラッシュ前の任意の F-RAM 消去

セクション 3 には、**「フラッシュ前に永続化 F-RAM も消去する」**という
チェックボックスがあります——デフォルトはオフです。チェックすると、
更新シーケンスが開始する前に、ボードの板載 FM24CL64B 永続化 F-RAM へ
マジックペイロード消去コマンド（`0x192`——`docs/CANBUS.TXT` 参照）を
送信し、保存されているツールパラメータの状態を消去します。

**通常の更新には不要です。** 保存済みレコード自身のレイアウトにおける
バージョンの不一致は、次回起動時にすでに検出され、安全に無視されます
（`src/F303-master/README.md` のパラメータ永続化セクション参照）——
このチェックボックスは、本当にまっさらな状態を実現するために存在する
のであり、それをスキップすると何かが壊れたままになるからではありません。

**アプリケーションが実行中のときのみ機能します**——ブートローダー自体
は `0x192` をまったく処理しません、`firmware_can_global_post.c` だけが
処理します。その上にある「ボードは現在アプリケーションを実行中」
チェックボックスがオフの場合、このチェックボックスは静かにスキップされ
ます（理由を説明するログの行とともに）。その場合、ボードはすでにブート
ローダー内にあると想定されるためです。

**確認の欠落はフラッシュを止めません。** 消去コマンド自身の確認フレーム
が 2 秒以内に返ってこない場合、これは警告として記録され、実際のファーム
ウェア更新はそれでも続行されます——消去は、本ツールの本当の目的の隣に
ある、副次的な、任意のステップであり、その自身の確認フレームが行方
不明になったからといって、それ以外は成功していた更新を中止すべきもの
ではありません。それが重要な場合は、別途 F-RAM の状態を確認してください
（`URTC Tester` 自身のクエリステートボタン）。

## 🔑 HMAC キー / HardwareID の変更

このツールは**署名鍵を一切持ちません**。URTC のビルドが各アプリケーション
イメージに署名し、その署名をイメージの隣の `<image>.manifest.json`
（`hmac_sha256`、加えて `<image>.sha256`）に公開します。フラッシャーはその
公開署名を送信し、sha256 がマニフェストと一致しないイメージは拒否します。
GitHub からイメージをダウンロードすると両ファイルも一緒に取得され、
`python tools/sync_firmware.py` が同梱の `firmware/` フォルダを URTC の
ビルドから更新します（`--check` で検証）。既定では URTC の最新リリースのアセットから一式を取得します（`--release TAG` で別のリリースを指定）。代わりにローカルフォルダ（例えばローカルの URTC ビルド）を引数として渡すこともできます。鍵が必要なのは、マニフェストの
ない自作イメージをベンチ用ボードに書き込む場合だけです。下記の
`urtc_config.json` に `hmac_key_hex` / `slave_hmac_key_hex` を設定して
ください。設定がない場合、そのイメージはブートローダーが持ち得ない鍵で署名
されるのではなく拒否されます。URTC の `docs/FIRMWARE_SIGNING.TXT` を参照。 公開されているイメージは公開の開発用鍵（`signing_key_kind: dev`）で署名されているため、これは共有鍵による検査です。イメージがその鍵の保持者によって作られたことは示しますが、誰であるかは示しません。非対称署名（Ed25519）は計画中で、実装されていません。

**またはスクリプトに触れずにこれらを上書きする：** `firmware/` の隣に
ある任意の `urtc_config.json` は、署名キー、HardwareID、そしてメモリ
マップの値を設定できます——異なるボードのリビジョン、ローテーションされ
たキー、または（メモリマップフィールドについて）デプロイごとに新しい
スクリプトバージョンを必要とせずに、本ツールを異なるチップバリアント
やパーティションスキームに適応させるのに便利です：
```json
{
  "hardware_id": "0x0303CC01",
  "hmac_key_hex": "555254432D4859445241...",
  "app_max_size": 114688,
  "bootloader_max_size": 32768,
  "flash_page_size": 2048,
  "bootloader_flash_addr": "0x08000000",
  "app_flash_addr": "0x08008000"
}
```
すべてのフィールドは任意です——実際に変更するものだけを上書きしてくだ
さい。欠落しているフィールドは、本ツール自身の組み込みデフォルトに
フォールバックします。**メモリマップと HardwareID のオーバーライドは、メインボード自身の定数にのみ適用されます**（唯一の例外は拡張スレーブの署名鍵 `slave_hmac_key_hex` で、これもここで設定できます）——拡張スレーブチップ自身の相当するもの
（`SLAVE_BOOTLOADER_FLASH_ADDR`、`SLAVE_APP_FLASH_ADDR`、
`SLAVE_HARDWARE_ID` など）は `flasher_config.py` 自体に固定されています。
そのハードウェア自身の実際の値は、メインボード自身のデフォルトのように
デプロイ時のオーバーライドを必要とするのではなく、すでにそれ自身の
リンカスクリプトに対して確認済みだからです。存在はするが壊れている
ファイルは警告をログに記録し、タイプミスでツールをクラッシュさせるの
ではなく、同様にフォールバックします。どのソースがアクティブかは起動時
にログに記録されるため、あるセッションが実際に使用した値は常に確認
できます。`hardware_id` は JSON 文字列（`"0x0303CC01"`）と、プレーンな
JSON 数値（`50580689`）のどちらも受け付けます——ファイルがどのように
生成されるかにとって、より自然な方でかまいません。`app_max_size`、
`bootloader_max_size`、`flash_page_size`、`bootloader_flash_addr`、
`app_flash_addr` も、上記の署名キーと HardwareID と並んでここで上書き
可能です——本ツールが将来異なるチップバリアントやパーティションスキーム
に適応される場合に便利です。

## 🔄 更新のしくみ

このプログラムは自分自身の新しいバージョンを探せます。「更新を確認」ボタンは GitHub に一度だけ問い合わせ、お使いのシステム向けで新しい場合にだけ署名付きパッケージを提案します。確認を有効にしない限り、何も自動では確認もインストールもされず、更新にはあなたの確認が必要です。パッケージは SHA-256 と、プログラムに固定されたリリース鍵の署名に一致しなければなりません。前のバージョンは保持され、新しいバージョンが起動しない場合は自動的に復元されます。`urtc-updater --cli package list|check|install|rollback` はコマンドラインからフラッシャーとテスターに対して同じことを行い、`install --file` はネットワークなしで動作します。
<!-- /urtc-section:updates -->

<!-- urtc-section:first_flash -->
## 🚦 ハードウェアなしの最初の書き込み

1. 仮想ボードを起動します：`python -m urtc_can.virtual_board`。
2. 別のターミナルで `URTC_VIRTUAL_PORT=socket://127.0.0.1:7777` を設定してフラッシャーを起動します。仮想ボードがポート一覧に表示されます。
3. それを選んで接続を押し、`firmware/` からイメージを選び（または参照して）CAN-OTA 開始を押します。
4. 仮想ボードは、実機と同じサイズ、署名、バージョンの検査を行いながら更新全体を受け付けます。これはモデルであり、実機では動かしていません。
<!-- /urtc-section:first_flash -->
